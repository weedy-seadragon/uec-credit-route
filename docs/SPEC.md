## 1. 概要

### 1.1 目的

電気通信大学の学生が、自分の「学年・類・教育プログラム・取得済み科目」を入力するだけで、**卒業までに何をどれだけ取ればよいか**（＝単位取得ルート）が一目で分かるWebサイトを作る。

学修要覧（PDF）とシラバス（Web）に散らばっている情報を一つのデータに統合し、「要覧を読み解く手間」をなくすことが本質的な価値。

### 1.2 背景・課題

- 学修要覧はPDFで100ページ超。卒業要件は別表に分散しており、類・プログラム・入学年度ごとに条件が違う。
- 学務情報システム（campusweb）は履修登録と成績参照はできるが、「あと何が足りないか」は教えてくれない。
- 先輩の口伝や非公式まとめに頼っている学生が多い。

### 1.3 ゴール（成功の定義）

1. 自分（Ⅰ類メディア情報学）の卒業要件チェックが正しく動く
2. 全類・夜間主のデータが揃い、電通大生なら誰でも使える
3. Twitter・友人の時間割アプリからリンクで飛べ、Google検索でも見つかる

### 1.4 対象外（やらないこと）

- 学務情報システムへの自動ログイン・スクレイピング（規約・セキュリティ上NG）
- 履修登録の代行
- 大学院（博士前期・後期）のカリキュラム（将来拡張の余地は残す）
- CAP制（履修登録単位の上限）のチェック
- 教職課程・副専攻の完全対応（初版では「参考情報」止まり）

## 4. 利用者とユーザーストーリー

### 4.1 想定利用者

| ペルソナ | 状況 | 知りたいこと |
|---|---|---|
| 1年生（一般） | 類は決定、プログラム未定 | 1年次必修を落としていないか。2年次審査は大丈夫か。どのプログラムに進むか |

### 4.2 ユーザーストーリー（優先度順）

1. 学生として、学年・類・プログラム・入学年度を選ぶと、自分に適用される卒業要件表が見たい
2. 学生として、取得済み科目をチェックしていくと、区分ごとの充足率が即座に更新されてほしい
3. 学生として、「次の学期に取るべき科目」を、必修→選択必修→不足区分の順に提案してほしい
4. 学生として、科目名をクリックしたらシラバスのページに飛びたい
5. 学生として、入力した履修状況をファイルに保存し、別の端末やブラウザで読み込みたい
6. 学生として、友人の時間割アプリで登録した科目を、そのまま本サイトに取り込みたい
7. 学生として、プログラム未定のとき、複数プログラムで「今の取得状況ならどれが近いか」を比較したい
8. 運用者として、新年度のシラバス公開後に半自動でデータを更新したい

## 5. 機能要件

優先度：**Must**（初版に必須）／ **Should**（初版に入れたい）／ **Could**（将来）

### F-1 プロフィール設定 [Must]

- 入力項目：入学年度、コース（昼間／夜間主）、類、教育プログラム（未定を許可）、現在の学年、推薦入学かどうか
- 入学年度から適用される要覧バージョン（要件セット）を自動決定する
- 類は入学時に確定しているので必須入力。プログラムは2年次後学期に配属されるため、1年生〜2年前期は「未定」がデフォルト。推薦入学者はプログラム確定済みとして入力できる
- プログラム「未定」の場合は、類の共通要件のみで判定し、F-6の比較機能へ誘導する
- 設定はブラウザに自動保存（localStorage）

### F-2 取得済み科目の入力 [Must]

入力手段は4つ。初版は (a)(b) 必須、(c)(d) はShould。

| 手段 | 内容 | 優先度 |
|---|---|---|
| (a) チェックリスト | 要件表の科目を一覧表示し、チェックを付ける。区分・学期でフィルタ可能 | Must |
| (b) JSONファイル読み込み／書き出し | 本サイト独自形式（§7.4）。書き出したファイルを別端末で読み込める | Must |
| (c) 友人アプリからの取り込み | 共通取り込み形式（§7.5）のJSONを受け取る。URLパラメータ or ファイル | Should |
| (d) 成績表テキスト貼り付け | 学務情報システムの成績照会画面をコピペ→科目名でマッチング | Could |

- 科目ごとに状態を持つ：`未履修` / `履修中` / `修得` / `不合格`
- 「履修中」は充足率の計算で「見込み」として別色表示する
- 科目名の表記ゆれ（全角半角、ローマ数字Ⅰ/I）を吸収する名寄せを行う

### F-3 要件充足チェック [Must]

- 適用要件セットの各区分について「必要単位／修得単位／履修中単位／不足単位」を計算し表示
- 表示は要覧の別表2と同じ並び順にする（要覧を見慣れた人が迷わない）
- 上位区分（例：総合文化科目 合計）と下位区分（例：人文・社会科学科目）の両方を判定
- 以下の**特殊ルール**に対応すること（要覧第2章で確認済み）
  - 選択必修「この科目群から△単位以上」。専門科目の選択必修を超過した分は選択科目に加算
  - **共通単位への繰り入れ**：各区分の超過分（昼間は人文・社会科学を除く）、理数基礎の選択科目（物理学演習第一・第二、化学概論第二）、言語文化応用科目Ⅱ、学外英語能力試験の認定単位は共通単位として数える。共通単位の必要数は別表2（Ⅰ類メディア 8、夜間主 6 など）
  - **同じ類の他プログラムの科目**は選択科目として算入できる（実験科目を除く）
  - **自由科目**（大学院連携科目、他類の専門科目など）は卒業要件に算入しない。取得単位には出すが「卒業に数えない」と明示する
  - 卒研着手審査の実験科目指定（例：プログラミング言語実験＋メディア情報学実験）と、2年次審査不合格時の履修不可科目（別表3の2）
  - 留学生向け科目（※印 FGN）は一般学生の候補に出さない
- 審査（2年次終了時／卒研着手／輪講履修／卒業）ごとに「現状で合格か」「不足は何か」を表示

### F-4 「残り」の提示（メイン画面） [Must]

メイン画面は一枚のリストで、上から次の順に並べる（§6参照）。

1. **取得単位**：修得済み科目の一覧
2. **不可の単位**：不合格になった科目の一覧（再履修候補）
3. **残りの必修**：未修得の必修科目（選択必修で不足がある区分の科目も含む）
4. **区分別の進捗**：「キャリア単位 2/4」のように、区分ごとに「修得／必要」を表示し、展開するとその区分で取れる未修得科目が出る。「選択」という一括りの見出しは作らない

**表示フィルタ**（画面右上）

ドロップダウン1つ。選択肢は「1年前期 … 4年後期」と「全学年」。

| 選択 | 動作 |
|---|---|
| 学期（例：3年前期） | 選んだ学期に**開講され、かつそのユーザーが履修できる**未修得科目だけを 3・4 に表示 |
| 全学年 | 卒業までに必要な未修得科目をすべて表示 |

不可になった科目は常に 3・4 にも表示する（再履修の対象なので隠す理由がない）。再履修用のスイッチは置かない。

**「履修できる」の判定**（学期切り替え時）

- 科目の開講期（前学期／後学期／通年）がフィルタの学期と一致する
- 科目の標準履修年次 ≤ ユーザーのその学期の学年（上の学年が下の学年の科目を取り直すのは可）
- 先修条件があれば満たしている（シラバスの先修科目欄。要覧に履修条件があればそれも）
- **標準年次より後で取る場合**は、その学年の必修科目と曜日時限が重ならないことを確認し、重なる場合は「○○（必修）と同時限」と警告を付けて表示する（非表示にはしない。判断はユーザーに委ねる）

**推奨の順位付け**：各セクション内は §8 のスコア順。「残りの必修」は標準年次が古い（＝遅れている）ものを上に。

- 「残りの必修」の各科目には理由ラベルを付ける。値は **「必修・未修得」「必修・再履修」の2種類のみ**（実験必修などの細分はしない）。それ以外の補足（「2年前期科目」、同時限警告）は理由ラベルとは別の欄に出す
- 「区分別の進捗」を展開した科目一覧には理由ラベルを付けない（区分名と n/m 表示で十分）
- 科目を「履修予定」にチェックすると F-3 の見込み計算と区分別進捗に反映される
- **更新ボタン**：チェック状態を確定し、localStorage に保存して全セクションを再計算する（自動保存でも良いが、明示的なボタンをスケッチ通り置く）

### F-5 科目一覧・詳細 [Must]

- 全科目を区分／学期／曜日時限／担当教員／キーワードで検索
- 科目詳細：シラバスの主要項目＋要件上の位置づけ（どの区分で何単位として数えるか）
- 外部リンク
  - シラバス：`https://kyoumu.office.uec.ac.jp/syllabus/{年度}/{学部コード}/{学部コード}_{科目ID}.html`
  - 学務情報システム：トップページへのリンク（ログイン必須のため深いリンクは張らない）
  - 時間割PDF：該当学期のPDFへのリンク
- 外部リンクは新規タブで開き、`rel="noopener"` を付与

### F-6 プログラム比較 [Should]

- プログラム未定のユーザー向け。同一類の全プログラムについて「現在の取得状況での充足率」「卒研着手までに追加で必要な単位」を並べて表示

### F-7 時間割ビュー → **削除**

- 友人の時間割アプリが時間割を担当し、取得済み単位の管理はしていないため、本サイトは「単位の管理と残りの提示」に特化する
- 曜日時限の情報は F-4 の同時限警告にのみ使う（グリッド表示はしない）

### F-8 データ保存・持ち運び [Must]

- 自動保存：localStorage（ブラウザごと）
- 手動保存：JSON書き出し（ファイル名例 `uec-credits_2025_I_media_20260903.json`）
- 読み込み時はスキーマバージョンを検証し、古い形式は変換する
- 「データを全消去」ボタン
- 共有URL：プロフィール＋取得科目IDを圧縮してURLに埋め込む [Could]。長くなるので初版は見送り可

### F-9 公開・SEO・共有 [Must]

- GitHub Pages で公開（`https://<user>.github.io/<repo>/`）。独自ドメインは任意
- 各ページに `<title>`、`meta description`、OGP（`og:title` / `og:description` / `og:image`）、`twitter:card` を設定
- `sitemap.xml`、`robots.txt` を配置
- 類・プログラムごとに固定URLを持つ（例 `/#/route/2025/I/media`）→ 検索流入とアプリからのリンク先に使える
- 免責表示：「非公式サイト。最終確認は学修要覧と教務課で」を全ページに

### F-10 データ更新パイプライン（運用者向け） [Should]

- 年1回（4月）と学期ごとに実行する想定
- 手順
  1. `GakkiIchiran_31_0.html` と `GakkiIchiran_32_0.html` の表を読み、時間割コード・科目名・学期・曜日時限・担当を取得（スクリプト。§3.2）
  2. 各時間割コードの個別ページ `{所属}/{所属}_{コード}.html` から単位数・科目コード・区分・開講年次・先修科目を取得し、`subjects.json` を生成（スクリプト）
  3. 学修要覧PDFから別表を抽出し `requirements.json` を作成（**半手動**。PDFの表は自動抽出が不安定なので、抽出結果を目視で直す前提）
  4. 科目番号（末尾記号を除く）で要覧とシラバスを突き合わせ、片方にしかない科目のレポートを出して手で解決（新設・廃止・名称変更の検出）
  5. 検証スクリプトでスキーマ・整合性チェック → コミット → 自動デプロイ
- スクレイピングはアクセス間隔を空け（1〜2秒）、`User-Agent` に連絡先を入れる。教務課サーバーに負荷をかけない
- 取得したシラバス本文は再配布しない。本サイトに載せるのはメタデータ（科目名・コード・単位・学期・曜日時限・担当・区分）とシラバスへのリンクのみ

### F-11 バージョン管理（入学年度ごとの要件） [Must]

- 要件セットは「入学年度」をキーに持つ。2022〜2026年度分の要覧PDFが公開されているので、最低でも2024・2025・2026を用意
- 科目マスタは「開講年度」をキーに持つ。過去年度の科目も参照できるようにする（留年・再履修対応）

## 7. データモデル

すべて静的JSON。サイトに同梱し、ビルド時に読み込む。

### 7.1 `subjects.json`（科目マスタ）

科目番号（末尾記号を除いた形、例 `COM405`）を主キーにする。要覧のカリキュラム表とシラバスの両方から作る。

```jsonc
{
  "schemaVersion": 1,
  "year": 2026,                       // 開講年度
  "subjects": [
    {
      "code": "COM405",               // 主キー：科目番号から末尾記号を除いたもの
      "codes": ["COM405a", "COM405e"],// 要覧・シラバスに現れる末尾付きの番号
      "name": "メディア情報学プログラミング演習",
      "nameEn": "Computer Programming on Media Informatics",
      "credits": 1,
      "standardSemester": 4,          // 科目番号の数字1桁目（1〜8）= 標準履修学期
      "standardYear": 2,              // = ceil(standardSemester / 2)
      "termType": "後学期",           // 学期番号の奇偶から：奇数=前学期 / 偶数=後学期。通年・ターム制は備考から
      "allowedYears": [2, 3, 4],      // 履修できる学年。省略時は standardYear 以上すべて
      "field": "COM",                 // 科目番号の先頭3文字
      "forInternational": false,      // ※印（FGN）なら true
      "eveningAllowed": true,         // カリキュラム表の ＃ 印
      "graduateLinked": false,        // 大学院連携科目（自由科目）
      "offerings": [                  // シラバス由来。年度・クラスごと
        { "timetableCode": "21124201", "faculty": "31", "term": "後学期", "slots": [{ "day": "金", "period": 3 }],
          "instructors": ["柳井啓司"], "prerequisites": ["コンピュータリテラシー"],
          "syllabusUrl": "https://kyoumu.office.uec.ac.jp/syllabus/2026/31/31_21124201.html", "updatedAt": "2026-09-19" }
      ]
    }
  ]
}
```

- 単位数・標準学期・区分は**要覧を正**とし、曜日時限・担当・先修科目・URLは**シラバスを正**とする
- 必修／選択はプログラムごとに違うので科目マスタには持たず、`requirements.json` 側で持つ

### 7.2 `requirements.json`（要件セット）

入学年度 × コース × 類 × プログラム ごとに1ファイル。中身は要覧の**別表2（単位数）＋付録Cカリキュラム表（科目の割り当て）＋別表3・4（審査）**をそのまま構造化したもの。

```jsonc
{
  "schemaVersion": 1,
  "entryYear": 2025,
  "course": "day",                    // day / evening
  "cluster": "I",                     // I / II / III / null（夜間主）
  "program": "media",                 // media / management / mathinfo / cs / design / security / telecom / electronic-info / control / robotics / mechanical / electronics / optics / physics / chemistry / null（未定）
  "programSuffix": "a",               // 科目番号の末尾記号
  "source": "学修要覧2025 別表2, 別表3, 別表4, 付録C C.3.1①",
  "totalCredits": 128,
  "commonCredits": 8,                 // 共通単位の必要数
  "groups": [
```

**充足計算の順序**

1. 各葉グループについて修得単位を集計（必修は「全科目修得」、選択は「単位数 ≥ required」）
2. 超過分を計算：`max(0, 修得 − required)`。`overflowToCommon !== false` のグループの超過分と `countAs: "common"` の単位を共通単位に合算
3. 自由科目（`countsTowardGraduation: false`）は合計に入れない
4. 総単位 = 各グループの `min(修得, required)` の和 ＋ `min(共通単位, commonCredits)`

## 8. 推奨ロジック仕様

入力：要件セット R、ユーザーの取得状況 U、対象学期 T、開講科目集合 S(T)
出力：推奨科目の順序付きリスト

```
0. 表示フィルタが「学期 T」のとき、S(T) ← 開講期が T に一致し、
     standardYear <= ユーザーの T 時点の学年 かつ allowedYears に含まれ、
     先修条件を満たす科目。「全学年」のときは S ← 全科目
1. 候補 C ← S(T) のうち、U で「修得」でない科目（status=failed も含む）
1'. c が standardYear より後の学年で履修される場合、
     その学年の必修科目（未修得のもの）と slots が重なれば clash(c)=true として警告を付ける
2. 各候補 c について優先度スコアを計算
     score(c) = w1 * [c が必修で未修得]
              + w2 * [c が「選択必修で不足がある区分」に属する]
              + w3 * (c が属する区分の不足単位 / その区分の必要単位)
              + w4 * [c の標準履修年次 <= ユーザーの学年]      # 遅れている科目を優先
              + w5 * [c の先修科目をすべて修得済み]
              - w6 * [c の曜日時限が履修中・履修予定と重複]
              - w7 * [c が属する区分がすでに上限に達している]
3. 審査の期限が近い条件（例：2年次終了時審査の1年次必修）に関わる科目は最上位に固定
4. score 降順に並べ、各科目に「理由」文字列（該当した項目のうち最大寄与のもの）を付ける
5. score 順のリストをそのまま返す（履修上限による切り詰めはしない。CAP制は対象外）
```

初期値は `w1=100, w2=50, w3=30, w4=20, w5=10, w6=40, w7=100` 程度から始め、自分のケースで自然な結果になるよう調整する。ロジックはUIから独立した純粋関数として実装し、テストしやすくする（§9.3）。

## 9. 技術構成

### 9.1 採用スタック

| レイヤ | 採用 | 理由 |
|---|---|---|
| 言語 | TypeScript | C++経験者なら型の考え方はそのまま使える。情報量が最多 |
| UI | React + Vite | 学習資料が多く、GitHub Pagesへのデプロイが簡単 |
| ルーティング | React Router（HashRouter） | GitHub Pagesは任意パスを返せないため `#/` 方式が安全 |
| 状態・保存 | React state + localStorage | サーバー不要 |
| スタイル | CSS Modules または Tailwind | どちらでも可。最初はプレーンCSSでもよい |
| データ更新スクリプト | Python（requests + BeautifulSoup + pdfplumber） | スクレイピングとPDF表抽出の定番。TypeScriptでも可 |
| テスト | Vitest | 要件判定と推奨ロジックの単体テスト |
| ホスティング | GitHub Pages + GitHub Actions | 無料。pushで自動デプロイ |

### 9.2 C++の位置づけ

- ブラウザで直接動くのは JS/TS のみ。**画面はTypeScriptで書く**
- 要件判定・推奨ロジックは、望むならC++で先にCLIとして試作してよい（入力：JSON、出力：JSON）。ロジックの正しさをC++で確かめてからTSに移植する、という使い方
- Emscripten（C++→WebAssembly）で本番に組み込むことも技術的には可能だが、ビルド環境の構築とJS⇄WASMのデータ受け渡しが初心者には重い。ロジック自体は軽いので、**初版ではやらない**

### 9.3 コード構成（案）

```
repo/
├─ data/                    # 生成されたJSON（サイトに同梱）
│   ├─ subjects/2026.json
│   ├─ requirements/2025-day-I-media.json
│   ├─ requirements/common-day.json     # 総合文化・実践教育の科目リスト（全プログラム共通）
│   └─ aliases.json
├─ scripts/                 # データ更新（Python）
│   ├─ fetch_syllabus.py
│   ├─ extract_youran.py
│   ├─ match_names.py
│   └─ validate.py
├─ src/
│   ├─ domain/              # 純粋ロジック（UI非依存）
│   │   ├─ requirements.ts  # 充足判定
│   │   ├─ recommend.ts     # 推奨
│   │   └─ importers.ts     # 各形式の取り込み
│   ├─ pages/
│   ├─ components/
│   └─ storage/             # localStorage / JSON入出力
├─ tests/
└─ .github/workflows/deploy.yml
```

`src/domain/` は React に依存させない。ここだけは C++ で書いたものをそのまま移植する対象。

## 10. 非機能要件

| 項目 | 要件 |
|---|---|
| 性能 | 科目マスタ（数千件）を読み込んでも初回表示3秒以内。検索はクライアント側で即時 |
| 対応環境 | スマホ（iOS Safari / Android Chrome）とPC。学生の主な閲覧はスマホと想定しモバイルファースト |
| オフライン | 一度読み込めば通信なしで動く（静的サイトなので自然に満たせる。PWA化はCould） |
| プライバシー | 履修データはユーザーの端末にのみ保存。サーバー送信なし。アクセス解析を入れる場合は明示 |
| 正確性 | データの出典と取得日を `/about` に明記。要件セットに `source` を持たせ、画面からも参照可能にする |
| 免責 | 全ページに非公式である旨と「最終確認は要覧・教務課」の注記 |
| 著作権 | シラバス本文・要覧本文の転載はしない。メタデータとリンクのみ |
| アクセシビリティ | キーボード操作可、色だけに依存しない表示（✔✖などの記号併用） |
| 保守性 | データとロジックを分離。新年度対応はJSON追加で済む設計 |
